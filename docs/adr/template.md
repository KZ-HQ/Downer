# ADR-NNNN: A sentence naming the decision, not the topic

* Status: Proposed | Accepted | Accepted, superseded by [ADR-NNNN](NNNN-....md)
* Date: YYYY-MM-DD
* Issue: [KEI-NN](https://linear.app/kzhq/issue/KEI-NN)
* Amends / Supersedes / Follows: another ADR, when this one changes what it said

## Context

What was true before, and what forced a choice. Name the files and the
behaviour, not the feature request. A reader who has never seen the codebase
should finish this section understanding why doing nothing was not an option.

## What was measured

Only when something was. Numbers, the command or fixture that produced them,
and the date. A decision reconstructed from existing code says so here instead,
and says what evidence it rests on.

## Decision

The decision itself, in the present tense, with a heading per part when there is
more than one. Say what was rejected and why it lost — an ADR that lists only
the winner records an outcome, not a decision.

## Consequences

What follows: what changed in the code, what a future reader may rely on, what
got harder. Include the consequences that count against the decision.

## Unverified

What is asserted rather than established: untested platforms, unmeasured
alternatives, claims taken from a changelog rather than a run. Leave the heading
out only when there is genuinely nothing to put under it.
